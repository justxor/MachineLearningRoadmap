# 15. Multi-agent системы: когда они оправданы, а когда нет

Multi-agent — модный термин, который часто означает усложнение там, где оно не нужно. Несколько LLM, разговаривающих между собой, выглядят умно, но платят за это токенами, задержками и хрупкостью. Этот урок — про то, когда оно реально оправдано.

## Когда multi-agent оправдан

- **Чёткое разделение ролей**: planner / coder / reviewer. Каждый имеет свой системный промпт и набор tools.
- **Параллелизация независимых подзадач**: один агент исследует, другой пишет код.
- **Различные модели по специализации**: дешёвая модель для классификации, дорогая — для генерации.
- **Принципиально разные контексты**: один агент работает с CRM, другой — с биллингом.

## Когда multi-agent НЕ нужен

- Задача линейная — это просто пайплайн.
- Все агенты используют одну модель и пересекающиеся tools — это один агент с разными инструкциями.
- Параллелизм не нужен — последовательный код проще.
- Цена усложнения не окупается измеримым ростом качества.

## Паттерны

### Supervisor / orchestrator

Один "главный" агент решает, кому передать задачу. Остальные — специализированные.

```
user → supervisor → [coder | researcher | writer] → supervisor → user
```

Хорошо для задач с разными типами подзадач. Плохо — supervisor становится узким местом.

### Pipeline / handoff

Последовательная передача: agent_1 завершает свою часть и передаёт agent_2 с накопленным состоянием. Без супервизора.

Хорошо для жёстких workflow (например, генерация → проверка → правка). Плохо для адаптивных задач.

### Debate / cooperation

Несколько агентов спорят / договариваются о решении. Прокурор и адвокат. Дорого и медленно. Применять только если показано, что качество растёт.

### Hierarchy

Иерархия команд агентов: топ-менеджер ↔ тимлид ↔ исполнители. Обычно overengineering. Берегите себя.

## Цена сложности

Multi-agent имеет нелинейные эффекты:
- Стоимость растёт в N+ раз (каждое сообщение читается несколькими агентами).
- Latency растёт (последовательные шаги).
- Ошибки накапливаются: 0.95^5 ≈ 0.77.
- Дебаг превращается в кошмар.

## Антипаттерны

- "Сделаем 7 агентов, один из них — критик, один — стратег, один — креативщик". Это не архитектура, это игра в RPG.
- Агенты, разговаривающие между собой свободным текстом без structured handoff. Накапливают шум.
- Отсутствие глобального бюджета (steps, tokens, time) на всю мульти-агентную сессию.
- Не сравнивать с single-agent baseline.

## Практика

1. Возьмите задачу с явным разделением: research → write → review. Реализуйте как single-agent с цепочкой промптов и как multi-agent. Сравните качество, стоимость, latency.
2. Реализуйте supervisor с 3 специализированными агентами. Логируйте все handoff'ы.
3. Сделайте структурированный handoff: agent_1 возвращает JSON-объект, agent_2 принимает его на вход. Не свободный текст.
4. Введите общий бюджет: max_total_steps, max_total_cost. Спровоцируйте срабатывание.
5. Возьмите multi-agent систему и попытайтесь свернуть её в single-agent с tools. Замерьте, что потеряли.
6. Опишите ADR: почему именно multi-agent в вашем случае, а не один агент.

## Чек-лист

- [ ] Перед multi-agent я проверил single-agent baseline.
- [ ] Handoff между агентами структурирован, не свободный текст.
- [ ] Есть общий бюджет на всю сессию, не на каждого агента.
- [ ] Логи позволяют восстановить весь обмен между агентами.
- [ ] Усложнение оправдано измеримыми метриками.
