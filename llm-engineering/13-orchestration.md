# 13. Оркестрация агентов: LangGraph, state machines

Когда агент превращается из "цикл с tools" в граф состояний с условными переходами, ретраями, ветвлением и параллелизмом — нужна оркестрация. Голый цикл из урока 12 быстро превращается в ад при поддержке.

## Почему state machine

Агентный workflow — это конечный автомат:
- Узлы: шаги обработки (классификация → retrieval → генерация → проверка).
- Рёбра: переходы, в том числе условные.
- Состояние: данные, которые передаются между узлами.

Описание workflow как графа даёт:
- Визуализацию: видно, как идёт логика.
- Воспроизводимость: можно перезапустить с любого узла.
- Тестируемость: каждый узел тестируется отдельно.
- Параллелизм: независимые ветки выполняются одновременно.

## LangGraph

Основная Python-библиотека для агентной оркестрации.

```python
from langgraph.graph import StateGraph, END

class State(TypedDict):
    query: str
    docs: list[str]
    answer: str

g = StateGraph(State)
g.add_node("retrieve", retrieve_node)
g.add_node("answer", answer_node)
g.add_node("verify", verify_node)
g.set_entry_point("retrieve")
g.add_edge("retrieve", "answer")
g.add_conditional_edges("answer", lambda s: "verify" if needs_check(s) else END)
g.add_edge("verify", END)
graph = g.compile(checkpointer=memory)
```

Альтернативы: ваш собственный код. Для простых пайплайнов это нормально.

## Чекпойнты и возобновление

Серьёзный workflow должен переживать падения и перезапуски. LangGraph поддерживает checkpointer (Postgres, SQLite, Redis): после каждого узла состояние сохраняется. При падении — продолжаем с последнего checkpoint, не перевыполняя предыдущие шаги.

## Human-in-the-loop

В некоторых узлах нужно ждать решения человека: подтверждение действия, ввод данных. LangGraph поддерживает interrupt: workflow останавливается, ждёт сигнала, продолжается.

Это критично для агентов, которые делают что-то с реальным миром (отправка писем, изменение БД).

## Параллелизм

Независимые ветки — параллельно. Например, retrieval из 3 источников. Это сокращает latency, не повышает стоимость.

```python
g.add_node("search_wiki", search_wiki)
g.add_node("search_db", search_db)
g.add_node("search_web", search_web)
g.add_node("merge", merge_results)
# все три выполняются одновременно
```

## Антипаттерны

- Городить state machine для пайплайна из 2 шагов. Простой код понятнее.
- Огромный State, в котором лежит ВСЁ. Делайте State минимальным, артефакты — во внешнее хранилище.
- Без checkpoint'ов на долгих workflow. После падения начинаете сначала.
- "Магические" переходы, зависящие от LLM-решения, без логирования причины.

## Практика

1. Возьмите RAG-пайплайн из 4 шагов. Реализуйте на голом Python и на LangGraph. Сравните.
2. Добавьте условный узел: если уверенность ответа < 0.7, идём в verify, иначе в END.
3. Реализуйте чекпойнтер на SQLite. Намеренно убейте процесс посередине, перезапустите — убедитесь, что начали с правильного узла.
4. Добавьте human-in-the-loop на одобрение действия. Покажите, что происходит, если человек не отвечает 24 часа.
5. Сделайте параллельный fan-out: 3 retrieval'а одновременно, потом merge. Замерьте экономию latency.
6. Нарисуйте граф (LangGraph умеет в Mermaid). Положите в README репозитория.

## Чек-лист

- [ ] Workflow описан как граф, а не как лапша if/else.
- [ ] Есть чекпойнты для долгих процессов.
- [ ] Human-in-the-loop на деструктивных операциях.
- [ ] Независимые шаги выполняются параллельно.
- [ ] Граф визуализирован и понятен новому человеку.
