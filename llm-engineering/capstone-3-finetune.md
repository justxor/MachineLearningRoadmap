# Капстон 3. Fine-tune + локальный деплой специализированной модели

Возьмите узкую задачу, для которой большая облачная модель — оверкилл, и сделайте её на локальной маленькой fine-tuned модели. Цель — научиться выбирать, готовить данные, тюнить и деплоить, измеряя экономику и качество.

## Идеи задач

- Извлечение структурированных данных из документов одного типа (договоры, накладные).
- Классификация тикетов поддержки по 10–20 категориям.
- Генерация коротких саммари новостей в фиксированном формате.
- Преобразование естественного запроса в SQL для одной БД.

## Требования

### Функциональные

1. Датасет ≥ 500 примеров (train + val + test).
2. Baseline: промпт + большая модель.
3. Fine-tune минимум двух конфигураций (например, LoRA r=16 и r=32).
4. Локальный деплой через vLLM с OpenAI-compatible API.
5. Eval pipeline с автоматическим сравнением.

### Нефункциональные

1. Воспроизводимый рецепт (Makefile / scripts).
2. Версионирование: датасет, гиперпараметры, веса.
3. Документ "экономика": расчёт стоимости на 100k запросов для каждого варианта.
4. Документация: как обновить датасет и переобучить за < 1 час команды.

## Архитектура

```
[Data prep]
  raw → cleaning → format → train/val/test split → JSONL

[Training]
  base model + LoRA → fine-tune → checkpoints → eval

[Deployment]
  merge LoRA → quantize (опционально) → vLLM container → REST API

[Evaluation]
  baseline (cloud) vs fine-tuned (local)
  по: качеству, latency, стоимости

[Monitoring]
  Prometheus + Grafana → дашборд
```

## Этапы

1. **Неделя 1.** Сбор и подготовка датасета. Baseline на облачной модели.
2. **Неделя 2.** Первый прогон fine-tuning. Eval. Анализ ошибок.
3. **Неделя 3.** Итерации: разные гиперпараметры, чистка данных.
4. **Неделя 4.** Локальный деплой через vLLM. Замеры latency и стоимости.
5. **Неделя 5.** Документация, релиз.

## Метрики приёмки

- Fine-tuned маленькая модель достигает ≥ 95% качества baseline на узкой задаче.
- Стоимость на 1000 запросов: показано, во сколько раз дешевле.
- p95 latency локальной модели ≤ p95 baseline.
- Рецепт воспроизводим: один новый человек запускает за день.

## Что положить в резюме

- "Fine-tuned Llama 3.1 8B (LoRA r=16) на задаче извлечения данных из договоров. F1 = 0.92 vs 0.94 у GPT-4o, стоимость в 12× ниже, p95 latency в 3× ниже."
- Ссылка на репозиторий, инструкция по запуску.
- Отдельный документ с экономикой: TCO облако vs локально на 1M запросов в месяц.

## Распространённые ловушки

- Маленький грязный датасет → модель не учится / переобучается. Делайте чистку и аугментацию.
- Тюнили на одной формулировке промпта, продакшн использует другую — деградация. Покрывайте варианты.
- Запустили в Ollama в проде, упёрлись в throughput — переходите на vLLM.
- Не сохранили датасет вместе с весами — через месяц не воспроизведёте.
