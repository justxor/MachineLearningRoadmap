# 02. API провайдеров: OpenAI, Anthropic, Google, локальные

Выбор провайдера — это не "у кого моделька умнее", а компромисс между качеством, ценой, latency, приватностью, vendor lock-in и доступностью в вашем регионе. Решение должно быть осознанным.

## Большие провайдеры

**OpenAI** (GPT-4o, GPT-4o-mini, o1, o3). Лучшая экосистема инструментов, structured outputs, function calling. Хорошая русскоязычная поддержка. Минусы: цены, регуляции, в РФ — только через прокси.

**Anthropic** (Claude Opus, Sonnet, Haiku). Лучше работает с длинным контекстом и большими кодовыми базами. Аккуратнее с safety. Поддерживает prompt caching из коробки.

**Google** (Gemini 1.5/2.0 Pro, Flash). До 2M контекста, мультимодальность из коробки, дешёвые Flash-модели. Качество следования инструкциям иногда уступает конкурентам.

**xAI, Mistral, Cohere** — нишевые, но иногда оправданы по цене или фичам.

## Локальные и open-source

**Llama 3.1/3.3, Qwen 2.5, DeepSeek, Mistral, Gemma**. Через Ollama, vLLM, llama.cpp. Плюсы: приватность, нет vendor lock-in, низкие предельные издержки. Минусы: вы платите железом и временем команды.

Правило: если у вас не >100M токенов в месяц или жёсткие требования по приватности — локальный инференс редко окупается.

## Что сравнивать

- Цена за 1M входных / выходных токенов.
- Latency (TTFT — time to first token, и TPS — tokens per second).
- Лимиты RPM/TPM и стоимость их повышения.
- Поддержка structured output, function calling, streaming.
- SLA, доступность в вашем регионе, политика хранения данных.
- Качество на ВАШЕЙ задаче, а не на MMLU.

## Антипаттерны

- "Берём GPT-4o, потому что он самый умный". На простой классификации gpt-4o-mini или Haiku в 20 раз дешевле и не хуже.
- Хардкодить одного провайдера в коде. Через полгода захотите сменить — и не сможете.
- Сравнивать модели по бенчмаркам из твиттера, а не на своих данных.
- Не учитывать стоимость retry'ев и эвалов при оценке экономики.

## Унификация через абстракцию

Не пишите `openai.chat.completions.create` напрямую везде. Заведите единый клиент:

```python
class LLMClient(Protocol):
    def complete(self, messages: list, model: str, **kwargs) -> Completion: ...

# реализации: OpenAIClient, AnthropicClient, OllamaClient
```

Это даст вам: A/B тесты моделей, fallback при падении провайдера, единое логирование.

## Практика

1. Возьмите одну вашу задачу и прогоните её через 4 модели разных провайдеров. Замерьте latency, стоимость, качество на 20 примерах.
2. Реализуйте `LLMClient` как Protocol и две реализации: OpenAI и Anthropic. Покажите, что код задачи не меняется при смене провайдера.
3. Поставьте Ollama локально, скачайте `llama3.1:8b` и `qwen2.5:7b`. Прогоните ту же задачу.
4. Напишите decorator `@with_fallback(providers=[...])`, который при ошибке одного провайдера пробует следующего.
5. Соберите табличку: модель × задача × качество × цена за 1000 запросов × p50/p95 latency.
6. Защитите перед собой выбор: какую модель вы возьмёте в прод и почему. Запишите аргументы.

## Чек-лист

- [ ] Знаю цены минимум 4 моделей наизусть с точностью до порядка.
- [ ] Понимаю разницу TTFT и общего latency.
- [ ] Код приложения не знает, какой провайдер используется.
- [ ] Есть fallback на случай отказа основного провайдера.
- [ ] Качество выбранной модели измерено на МОИХ данных, а не на бенчмарках.
