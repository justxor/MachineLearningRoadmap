# 20. Стоимость, latency, кэширование, батчинг

LLM-фичи легко спалить бюджет компании. Большой запрос × миллион пользователей × несколько попыток ретраев = неприятный сюрприз для финдира. Этот урок про то, как держать инженерный контроль над экономикой.

## Бюджетирование

Считайте на запрос:
- Стоимость API = tokens_in × price_in + tokens_out × price_out.
- Стоимость инфраструктуры (vector DB, серверы, мониторинг).
- Стоимость retry'ев (особенно на structured outputs).
- Стоимость evals в CI.

На пользователя: median + p95 запросов в день × стоимость. На месяц: × 30. Прибавьте 30% запаса.

## Снижение стоимости

### Выбор модели

90% задач решаются `gpt-4o-mini` / `claude-haiku` / `gemini-flash` качественнее, чем кажется. Прогоняйте eval перед уходом на флагман.

### Routing

Простые запросы → дешёвая модель, сложные → дорогая. Классификатор сложности (можно дешёвой моделью или эвристикой) экономит много.

### Caching

- **Prompt caching у провайдеров**: для стабильных префиксов. 50–90% экономии на входных токенах.
- **Semantic cache**: хэширование по эмбеддингу запроса. Близкий запрос → готовый ответ. Аккуратно: false hits могут испортить опыт.
- **Кэш ответов RAG**: тот же вопрос за час — тот же ответ.

### Сокращение промпта

Большинство системных промптов раздуты в 2–3 раза. Сокращайте без потери качества (с прогоном тестов).

### Batching

Многие провайдеры поддерживают batch API (выполнение пачки запросов с задержкой за 50% цены). Идеально для оффлайн-задач: разметка, eval, переиндексация.

## Latency

### Метрики

- **TTFT** (time to first token): критично для UX в чатах.
- **TPS** (tokens per second): после первого токена.
- **TTLT** (time to last token): общая длительность.
- **p50/p95/p99**: распределение, не среднее.

### Снижение latency

- **Streaming**: пользователь видит первый токен через 0.5с, не ждёт 10с.
- **Параллелизм**: независимые вызовы — одновременно.
- **Speculative execution**: пока ждёте retrieval, начинайте генерацию заглушки.
- **Меньше токенов на выходе**: `max_tokens` + явная инструкция "коротко".
- **Меньше шагов агента**: переосмыслите архитектуру.

### Локальная модель

Маленькая локальная модель может быть быстрее облачной по TTFT (нет сети, нет очередей). Особенно полезно для классификации/роутинга.

## Антипаттерны

- "Поставим гпт-4 везде и забудем". Через месяц придёт счёт.
- Streaming не используется, пользователь ждёт молча 10 секунд.
- Кэш без инвалидации. Через неделю отвечает устаревшее.
- Не различать дорогие и дешёвые операции в логах. Не поймёте, что съело бюджет.
- Не выставлять max_tokens. Модель пишет эссе вместо ответа.

## Практика

1. Замерьте текущую стоимость на 1000 запросов вашего приложения. Декомпозируйте по этапам.
2. Внедрите prompt caching для стабильного префикса. Замерьте экономию.
3. Сделайте routing "лёгкая модель / тяжёлая" с классификатором. Замерьте экономию и потери качества.
4. Реализуйте streaming в UI. Замерьте субъективное улучшение UX.
5. Сократите системный промпт в 2 раза без падения метрик.
6. Настройте dashboard со стоимостью в реальном времени по пользователям и фичам.

## Чек-лист

- [ ] Знаю стоимость одного типичного запроса с точностью до центов.
- [ ] Использую дешёвые модели там, где они справляются.
- [ ] Включён prompt caching на стабильных префиксах.
- [ ] Streaming работает в пользовательском UI.
- [ ] Есть max_tokens на всех вызовах.
