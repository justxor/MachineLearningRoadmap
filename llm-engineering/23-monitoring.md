# 23. Мониторинг LLM-приложений в проде

После выкатки начинается главное: жить с системой, ловить деградации, разбирать инциденты. Без правильного логирования и мониторинга LLM-приложение превращается в чёрный ящик, в который страшно лезть.

## Что логировать

Каждый вызов:
- timestamp, request_id, user_id, session_id.
- Модель, версия промпта, температура.
- Полный prompt (с redacted PII).
- Полный ответ.
- Tools, которые вызывались, аргументы, результаты.
- Tokens in/out, стоимость.
- Latency: TTFT, TTLT.
- Любые ошибки.

Если потом нельзя восстановить ровно, что произошло — логов недостаточно.

## Tracing

Один пользовательский запрос — это часто несколько LLM-вызовов + retrieval + tool calls. Используйте distributed tracing: один `trace_id` связывает все вызовы.

Инструменты: Langfuse, Phoenix, Arize, OpenTelemetry с кастомным инструментированием.

```python
with tracer.span("retrieve") as span:
    docs = retrieve(query)
    span.set_attribute("doc_count", len(docs))
with tracer.span("generate") as span:
    answer = llm.complete(prompt(query, docs))
    span.set_attribute("tokens_out", answer.usage.completion_tokens)
```

## Метрики и дашборды

Минимальный дашборд:
- Запросов в минуту (по фичам).
- Стоимость в день / в неделю.
- Latency p50/p95/p99 (по фичам, по моделям).
- Error rate (общий и по типам).
- % thumbs down.
- % fallback на запасной провайдер.
- GPU utilization (если локальный инференс).

## Алёрты

Что должно будить дежурного:
- p95 latency × 2 от обычного на 10 минут.
- Error rate > 5% на 5 минут.
- Стоимость в час > X (бюджетные).
- Полное падение провайдера → fallback не сработал.
- % thumbs down резко вырос (drift качества).
- GPU OOM, restarts.

Не алёртить на: единичные ошибки, длинные ответы пользователей, обычные пики траффика.

## Drift

Распределение запросов меняется со временем. Новые типы вопросов, новый сленг, новые edge cases. Регулярно:
- Семплируйте N запросов в неделю, отсматривайте.
- Кластеризуйте новые запросы (через эмбеддинги) — увидите новые кластеры.
- Сравнивайте онлайн-метрики с baseline по неделям.

## Инциденты

Когда что-то сломалось:
1. По логам выясняем, что именно сломалось (модель, prompt, tool, retrieval, провайдер).
2. Если можно — откат к предыдущей версии в одну команду.
3. Если нельзя — feature flag отключает проблемную часть.
4. Post-mortem: что случилось, почему не поймали раньше, как чинить процесс.

## Антипаттерны

- Логировать только request/response, без tokens, latency, версии промпта.
- Хранить логи 7 дней. Для дебага редких багов нужно 30–90.
- Не редактировать PII в логах. Утечка ждёт.
- Алёрты на всё подряд — alert fatigue, важное теряется.
- Не пересматривать дашборды и алёрты. Через год они не соответствуют системе.

## Практика

1. Подключите Langfuse / Phoenix к своему приложению. Залогируйте 1000 запросов.
2. Постройте дашборд с latency, cost, error rate. Покажите команде.
3. Настройте 5 ключевых алёртов. Намеренно спровоцируйте каждый — убедитесь, что приходит уведомление.
4. Сделайте post-mortem template и пройдите его на одном из прошлых инцидентов (или придуманном).
5. Запустите еженедельный sampling: 50 случайных запросов отсматриваются вручную.
6. Опишите runbook: что делать при отказе провайдера, при росте error rate, при росте стоимости.

## Чек-лист

- [ ] Каждый вызов LLM логируется с полным контекстом.
- [ ] Tracing связывает все вызовы одной пользовательской сессии.
- [ ] Дашборд с ключевыми метриками доступен команде.
- [ ] Алёрты настроены и срабатывают по делу.
- [ ] Есть runbook для типичных инцидентов.
