# 16. Evals: оффлайн-метрики качества LLM-систем

LLM-приложение без evals — это код без тестов. На демках работает, в проде ломается, при изменении промпта непонятно, лучше стало или хуже. Evals — главное отличие инженера от энтузиаста.

## Что такое eval

Eval — это автоматический прогон системы на наборе примеров с измеримой оценкой результата. Бывает:
- **Detерминированный**: точные сравнения (классификация, извлечение, exact match).
- **Семантический**: similarity, BLEU, ROUGE — для генерации.
- **LLM-as-judge**: другая LLM оценивает ответ (см. следующий урок).
- **Человеческая разметка**: эталон.

## Структура eval-датасета

```yaml
- id: contract_extract_01
  input: "Договор от 12.03.2024 между ООО Ромашка..."
  expected:
    date: "2024-03-12"
    parties: ["ООО Ромашка", "ИП Иванов"]
  tags: ["contract", "ru", "easy"]
- id: contract_extract_02
  input: "Контракт #441/2024..."
  expected:
    date: "2024-04-15"
  tags: ["contract", "ru", "hard"]
```

Минимум — 30 примеров. Хорошо — 200+. Покрывайте edge cases, не только happy path.

## Метрики

| Тип задачи | Метрика |
|---|---|
| Классификация | accuracy, F1, precision/recall |
| Извлечение | exact match, field-level F1 |
| Генерация (есть эталон) | ROUGE, BLEU, BERTScore |
| Генерация (свободная) | LLM-as-judge, human eval |
| RAG | faithfulness, answer relevance, context recall |
| Tool use | tool_choice_accuracy, args_match |

## Инструменты

- **promptfoo**: CLI-утилита, простая, хороша для запуска evals в CI.
- **ragas**: специализирована для RAG-метрик.
- **DeepEval**, **Braintrust**, **Langfuse**: платформы с UI.
- **Свой скрипт**: тоже валидный вариант на 30 кейсов.

## Eval в CI

Каждый PR с изменением промпта → прогон evals → метрики комментируются в PR. Откат, если есть значимая регрессия.

```yaml
# .github/workflows/evals.yml
- run: promptfoo eval -c promptfoo.yaml
- run: promptfoo eval --threshold pass=0.85
```

## Версионирование результатов

Храните результаты прогонов: дата, промпт-версия, модель, метрики, примеры с ошибками. Это история качества вашей системы. Без неё вы не увидите медленную деградацию.

## Антипаттерны

- "Покрутил в чате — работает". Без evals регрессии прилетят в прод.
- Eval на 5 примерах. Шумит. Минимум 30, лучше 100+.
- Только happy path. Edge cases — там, где ломаются деньги.
- Метрики не отражают пользовательский опыт. Считайте то, что важно бизнесу, а не то, что легко.
- Не проверять стабильность: один прогон ≠ метрика. Запускайте N раз, считайте дисперсию.

## Практика

1. Соберите 50 примеров для своей задачи: вход, эталон, теги.
2. Реализуйте автоматический прогон + расчёт метрик.
3. Подключите промпт v1 и v2. Замерьте разницу. Решите, чем выкатывать.
4. Найдите 10 примеров, где система ошибается, и поймите паттерн.
5. Добавьте eval в pre-commit или CI. Покажите, что регрессия блокирует мердж.
6. Запустите тот же eval 5 раз. Посмотрите на дисперсию метрик. Если шум большой — поднимите размер выборки или температуру=0.

## Чек-лист

- [ ] Есть eval-датасет ≥ 30 примеров.
- [ ] Метрики автоматически считаются и логируются.
- [ ] Eval запускается в CI и блокирует регрессии.
- [ ] Edge cases покрыты, не только happy path.
- [ ] Стабильность метрик измерена (дисперсия по N прогонам).
