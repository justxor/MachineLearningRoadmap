# 08. Эмбеддинги и векторные базы данных

Эмбеддинги — это представления текста в виде векторов фиксированной размерности, в которых близкие по смыслу тексты находятся рядом в пространстве. Векторная БД — это хранилище, оптимизированное для поиска ближайших соседей. Без понимания их работы RAG превращается в чёрный ящик.

## Выбор модели эмбеддингов

Критерии:
- Поддержка вашего языка (для русского многие OpenAI/Cohere модели — ОК, но не всегда лучший выбор).
- Размерность (768, 1024, 1536, 3072). Меньше — дешевле хранение и быстрее поиск.
- Длина входа (обычно 512–8192 токенов).
- Open-source vs API.

Хорошие варианты:
- API: `text-embedding-3-large` (OpenAI), `voyage-3` (Voyage AI).
- Open-source: `bge-m3`, `e5-mistral`, `multilingual-e5-large`.

## Косинусное сходство

`similarity = (a · b) / (|a| × |b|)`. От -1 до 1, обычно нормализуют к 0..1. Это базовая метрика для поиска. Не панацея: вектор "цена дома 100к" близок к "цена дома 100млн".

## Векторные базы данных

| БД | Когда брать |
|---|---|
| **pgvector** | У вас уже есть Postgres. Работает до десятков млн векторов. |
| **Qdrant** | Хороший баланс фич и простоты. Filtering, гибридный поиск. |
| **Weaviate** | Богатые фичи, hybrid search из коробки. |
| **Milvus** | Когда нужны сотни млн–миллиарды векторов. |
| **FAISS** | Локально, в памяти, для прототипов. Не БД. |
| **Pinecone** | SaaS, не хотите DevOps. Дорого. |

Для 90% задач хватит pgvector или Qdrant. Не берите Pinecone "на всякий случай".

## Индексы ANN

Полный перебор медленный. Используются приближённые алгоритмы:
- **HNSW**: быстрый, точный, жрёт RAM. Дефолт.
- **IVF**: дешевле по памяти, медленнее.
- **PQ / SQ**: квантование для уменьшения размера.

Trade-off: recall ↔ скорость ↔ память. Замеряйте recall@K после построения индекса.

## Фильтры

Векторного поиска недостаточно. Нужны атрибутные фильтры: `team_id = 42 AND date > 2024-01-01`. Поддержка фильтров и их производительность — критерий выбора БД.

## Антипаттерны

- Использовать дефолтный `text-embedding-ada-002` "потому что туториал". Он устарел.
- Хранить эмбеддинги в обычной БД и делать full-scan. На 100k векторов уже больно.
- Перегенерировать эмбеддинги для всего корпуса при каждом изменении одного документа.
- Не нормализовать векторы при использовании dot product вместо cosine.
- Считать, что 3072-мерные векторы всегда лучше 768-мерных.

## Практика

1. Поставьте pgvector локально через Docker. Создайте таблицу с эмбеддингами.
2. Возьмите 1000 русскоязычных коротких документов. Прогоните через 3 модели эмбеддингов. Сравните recall@5 на 50 запросах.
3. Замерьте latency поиска при размерах индекса 10k, 100k, 1M (можно дублировать).
4. Постройте HNSW индекс. Сравните recall и скорость с full-scan.
5. Реализуйте инкрементальное обновление индекса при добавлении документа.
6. Сделайте поиск с фильтром по метаданным (`source = "docs"`). Замерьте, насколько падает скорость.
