# 11. Tools / function calling: основы

Tools (они же function calling) — это механизм, через который LLM умеет вызывать внешние функции: API, БД, поиск, расчёты. Без tools LLM — это чат-болталка. С tools — это инструмент автоматизации.

## Как это работает

1. Вы передаёте модели список доступных функций (имя, описание, JSON schema аргументов).
2. Модель решает, нужна ли функция, и если да — какая и с какими аргументами.
3. Вы выполняете функцию в своём коде и передаёте результат модели.
4. Модель формулирует финальный ответ или вызывает следующую функцию.

Модель **не выполняет** функции сама. Она лишь говорит "вызови такую-то". Безопасность — на вас.

## Пример

```python
tools = [{
    "name": "get_weather",
    "description": "Get current weather in a given city.",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"]
    }
}]

response = client.messages.create(
    model="claude-3-5-sonnet-latest",
    tools=tools,
    messages=[{"role": "user", "content": "Какая погода в Москве?"}]
)
# response.content содержит tool_use с {"city": "Москва"}
```

## Описания функций

Описание — это часть промпта, которую читает модель. От него зависит, поймёт ли модель, когда использовать функцию.

Плохо: `"description": "Get weather"`.

Хорошо: `"description": "Returns current weather (temperature in C, conditions, wind) for a given city. Use when user asks about weather, temperature, or whether to dress warmly. Returns null if city is unknown."`

Описывайте, КОГДА вызывать, что вернётся, и что делать при ошибке.

## Обработка ошибок

Функция может вернуть ошибку (нет связи, невалидный аргумент, нет данных). Не возвращайте exception в виде traceback — отдайте структурированную ошибку, которую модель поймёт:

```python
{"error": "city_not_found", "message": "City 'Атлантида' is not in our database. Suggest user verify spelling or try a different city."}
```

## Идемпотентность и безопасность

LLM может вызвать функцию повторно, не туда или с мусором. Защита:
- Идемпотентные операции (POST с idempotency_key).
- Whitelist допустимых аргументов.
- Подтверждение пользователя для деструктивных операций (delete, send_money).
- Ограничения скорости (rate limiting).

## Антипаттерны

- Передавать модели 50 функций сразу. Качество выбора падает после 10–15.
- Описания на 1 строчку. Модель не понимает, когда вызвать.
- Возвращать функции, которые могут трогать прод-данные без подтверждения.
- Использовать tools для того, что можно зашить в промпт (например, текущая дата).

## Практика

1. Реализуйте 3 простых tools: `get_time`, `calculator`, `web_search` (фейковый OK). Подключите к чату.
2. Намеренно дайте плохое описание одного из tools. Посмотрите, когда модель путается.
3. Сделайте tool с ошибкой (например, `get_weather("ХХХ")` возвращает структурированную ошибку). Проверьте, обрабатывает ли модель.
4. Реализуйте идемпотентный `create_ticket(idempotency_key, ...)`. Проверьте, что двойной вызов даёт один тикет.
5. Сделайте механизм human-in-the-loop: tool `delete_record` требует подтверждения через CLI.
6. Замерьте, как растёт стоимость с числом tools (системный промпт увеличивается).

## Чек-лист

- [ ] Описания функций объясняют КОГДА вызывать.
- [ ] Ошибки возвращаются структурированно, не traceback'ом.
- [ ] Деструктивные операции требуют подтверждения.
- [ ] Число tools на один вызов — в разумных пределах (≤15).
- [ ] Tools версионируются и тестируются как код.
