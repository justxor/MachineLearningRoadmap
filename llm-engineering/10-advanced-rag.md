# 10. Продвинутый RAG: query rewriting, HyDE, multi-hop

Baseline RAG (chunk → embed → top-K → generate) ломается на сложных запросах: коротких ("как настроить?"), многошаговых ("сравни X и Y по Z"), на тех, где пользователь использует свой жаргон, а документы — корпоративный. Продвинутые техники чинят это.

## Query rewriting / expansion

LLM переписывает запрос в более удобный для поиска вид. Часто — несколько вариантов сразу.

```python
def rewrite_query(query: str) -> list[str]:
    return llm.complete(f"""Перефразируй запрос для поисковой системы 3 разными способами.
Запрос: {query}
Верни JSON-массив строк.""")
```

Все варианты ищем параллельно, результаты объединяем через RRF.

## HyDE (Hypothetical Document Embeddings)

Парадоксальная техника: вместо поиска по запросу, LLM сначала генерирует ГИПОТЕТИЧЕСКИЙ ответ. Эмбеддинг этого ответа используется для поиска. Идея: гипотетический ответ ближе по структуре к документу, чем запрос.

```python
hypothetical = llm.complete(f"Ответь кратко на: {query}")
docs = vector_search(embed(hypothetical), k=5)
final = llm.complete(prompt_with_context(query, docs))
```

Работает хорошо на коротких запросах. Дороже на 1 вызов LLM.

## Multi-hop RAG

Когда ответ требует нескольких шагов поиска. Запрос "у кого из CEO компаний топ-5 капитализации есть PhD?" нельзя ответить одним поиском.

Подход: LLM-планировщик разбивает на подзапросы, каждый — отдельный retrieval, результаты собираются. Близко к агентам с инструментом search.

## Self-querying / metadata extraction

LLM из естественного запроса выделяет фильтр и собственно поиск. "Покажи документы по безопасности за 2024" → `{filter: {topic: "security", year: 2024}, query: "..."}`. Это убирает зависимость от того, что эмбеддинг "поймёт год".

## Adaptive retrieval

Не всегда нужен retrieval. Сначала LLM решает: "нужен ли мне поиск?". Простые вопросы ("привет") идут мимо. Экономия и качество.

## Contextual retrieval (Anthropic)

Перед эмбеддингом каждый чанк дополняется коротким контекстом из родительского документа (LLM генерирует на этапе индексации). Резко поднимает recall на чанках, где смысл зависит от контекста.

## Антипаттерны

- Внедрять HyDE/multi-hop, не имея baseline и evals. Вы не поймёте, помогло ли.
- Делать query rewriting на каждом запросе, включая простые. Дорого без пользы.
- Multi-hop без ограничения на число шагов. Получите бесконечные циклы.
- Использовать все техники сразу. Сложность растёт быстрее качества.

## Практика

1. Возьмите baseline RAG и 50 сложных запросов из реальных логов. Замерьте Recall@5 и качество ответа.
2. Реализуйте query rewriting с 3 вариантами + RRF. Сравните.
3. Реализуйте HyDE. Замерьте улучшение и удорожание.
4. Реализуйте adaptive retrieval (классификатор "нужен ли поиск"). Замерьте экономию.
5. Сделайте multi-hop для 5 запросов с известной структурой шагов. Ограничьте глубину 3 шагами.
6. Постройте таблицу: техника × качество × стоимость × latency. Решите, что идёт в прод.
