# 03. Промпт-инжиниринг как инженерная дисциплина

Промпт-инжиниринг — это не "магические формулировки", не "10 техник от гуру" и не "скажите модели, что её папа умрёт, если она не ответит правильно". Это итеративная инженерная работа: гипотеза → набор тестов → измерение → улучшение.

## Базовая структура промпта

1. **Системное сообщение**: роль, цель, ограничения, формат вывода.
2. **Контекст**: данные, документы, история.
3. **Инструкция**: что конкретно сделать.
4. **Few-shot примеры**: 2–5 показательных пар вход/выход.
5. **Запрос**: текущий вход.

Не пихайте всё в одно сообщение. Структурируйте через секции (XML-теги или markdown).

```
<role>Ты — извлекатель структурированных данных из юридических документов.</role>
<task>Извлеки стороны договора, дату, сумму. Верни JSON.</task>
<examples>
вход: "Договор от 12.03.2024 между ООО Ромашка и ИП Иванов на 100 000 руб."
выход: {"date": "2024-03-12", "parties": ["ООО Ромашка", "ИП Иванов"], "amount": 100000}
</examples>
<input>{{document}}</input>
```

## Техники, которые реально работают

- **Few-shot**: 3–5 примеров поднимают качество сильнее, чем переформулировка инструкции.
- **Chain-of-thought**: "рассуждай пошагово" — работает на задачах с логикой. На простых классификациях замедляет и удорожает без выгоды.
- **Структурированный вывод (JSON schema, XML)**: убирает 90% боли с парсингом.
- **Декомпозиция**: одна задача → один промпт. Сложные цепочки лучше явных, чем "всё в одном вызове".
- **Self-consistency**: запустите 5 раз с temperature>0, возьмите большинство. Дорого, но повышает качество.

## Что НЕ работает (или работает плохо)

- Угрозы и эмоциональный шантаж. Современные модели на них реагируют слабо или непредсказуемо.
- "Ты — эксперт мирового уровня с 30 годами опыта". Это шум. Конкретная роль и задача — да, регалии — нет.
- Длинные общие инструкции "будь точным, будь полезным, не ври". Это не уменьшит галлюцинации.
- Копирование чужих промптов без адаптации под свою модель и задачу.

## Версионирование промптов

Промпт — это код. Храните в git, версионируйте, тестируйте.

```
prompts/
  extract_contract/
    v1.txt
    v2.txt
    tests.yaml
```

При деплое: `PROMPT_VERSION=v2`. При регрессии: откат на v1 в одну команду.

## Антипаттерны

- Менять промпт по ощущениям без evals. "Кажется, стало лучше" — не метрика.
- Один гигантский промпт на все случаи жизни вместо набора специализированных.
- Хардкодить промпты в коде, рядом с бизнес-логикой.
- Не логировать промпты и ответы в проде. Без них вы слепы.

## Практика

1. Возьмите задачу классификации. Напишите v1-промпт без примеров, v2 с 3 few-shot. Сравните на 50 примерах.
2. Реализуйте chain-of-thought для задачи арифметики из 3 шагов. Сравните с прямым ответом.
3. Заведите папку `prompts/` с версионированием. Подключите через шаблонизатор (Jinja2).
4. Напишите 10 тестов в YAML формата "вход → ожидание". Прогоните оба промпта.
5. Реализуйте self-consistency: N запусков, majority vote. Замерьте, на каких задачах помогает.
6. Возьмите свой реальный промпт и сократите его в 2 раза без потери качества. Зафиксируйте метрики до/после.

## Чек-лист

- [ ] Все промпты лежат в репозитории, версионируются.
- [ ] Под каждый промпт есть набор тестов.
- [ ] Знаю, какие техники помогают на МОИХ задачах, а не вообще.
- [ ] В проде логируется промпт, ответ, версия.
- [ ] Не меняю промпт без прогона тестов.
