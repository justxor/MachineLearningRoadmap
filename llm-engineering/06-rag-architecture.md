# 06. Архитектура RAG: когда и почему

RAG (Retrieval-Augmented Generation) — это паттерн, где LLM получает релевантный контекст из внешнего источника перед генерацией ответа. Не магия, не serebryanyi bullet, а инженерный компромисс.

## Когда нужен RAG

- Данные обновляются чаще, чем модели переобучаются.
- Нужны ссылки на источники в ответе.
- Объём знаний > контекстного окна.
- Требуется контроль доступа: разные пользователи видят разные документы.

## Когда RAG НЕ нужен

- Знания стабильны и помещаются в системный промпт — просто положите в промпт.
- Задача требует ОБЩИХ рассуждений, а не извлечения фактов.
- Данные малы (<50 страниц) — long context + prompt caching дешевле.
- Нужно специфическое поведение (стиль, формат) — это fine-tuning, не RAG.

## RAG vs Fine-tuning vs Long Context

| Критерий | RAG | Fine-tuning | Long context |
|---|---|---|---|
| Свежесть данных | + | − | + |
| Контроль источников | + | − | + |
| Стиль/формат | − | + | ± |
| Стоимость на запрос | низкая | низкая | высокая |
| Сложность поддержки | средняя | высокая | низкая |

В 90% случаев в проде вы хотите RAG. Fine-tuning — когда RAG не вытягивает.

## Канонический пайплайн RAG

1. **Индексация (offline)**: документы → чанки → эмбеддинги → векторная БД.
2. **Retrieval (online)**: запрос → эмбеддинг → top-K ближайших чанков.
3. **Augmentation**: чанки + запрос → промпт.
4. **Generation**: LLM генерирует ответ со ссылками.

Каждый шаг ломается по-своему. Без evals вы не узнаете, где именно.

## Где обычно ломается

- **Чанкование**: разрезали в неправильном месте, потеряли смысл.
- **Эмбеддинги**: используются для одного языка, спрашивают на другом.
- **Retrieval**: K слишком мал — пропустили факт; слишком велик — модель тонет в шуме.
- **Reranking**: не используется, и top-5 — мусор.
- **Generation**: модель игнорирует контекст и галлюцинирует.

## Метрики

- **Retrieval**: Recall@K, MRR, NDCG.
- **Generation**: faithfulness (нет ли галлюцинаций), answer relevance, context utilization.
- **Системные**: latency p50/p95, стоимость на запрос.

Без замера всех трёх уровней вы не поймёте, где улучшать.

## Антипаттерны

- "Сделаем RAG и заживём". Без evals — это лотерея.
- Использовать только косинусное сходство и top-3. Плохо работает на 80% реальных данных.
- Не показывать пользователю источники. Доверие падает, проверить нельзя.
- Считать, что "если есть в индексе — значит, найдётся". Recall редко 100%.

## Практика

1. Возьмите 20 документов и набор из 30 вопросов с известными правильными чанками. Это ваш золотой датасет.
2. Реализуйте baseline RAG: chunk по 500 токенов, OpenAI embeddings, FAISS, top-3. Замерьте Recall@3.
3. Прогоните ответы LLM и сделайте ручную разметку faithfulness на 30 примерах. Запишите baseline.
4. Возьмите 5 реальных запросов, где baseline ошибается. Найдите, на каком этапе пайплайна теряется качество.
5. Соберите архитектурное решение: какие модули, какие интерфейсы, как версионировать индекс.
6. Напишите ADR (architecture decision record): почему RAG, а не fine-tuning или long context, для вашей задачи.
