# 18. Онлайн-метрики, A/B-тесты, обратная связь от пользователей

Оффлайн-метрики говорят, как система работает на тестовом наборе. Прод покажет, как она работает в реальности. Без онлайн-метрик вы оптимизируете не то.

## Что мерить онлайн

### Поведенческие

- CSAT / thumbs up/down рядом с ответом.
- Доля диалогов, дошедших до escalate к человеку.
- Длительность диалога, число шагов до решения.
- Retention пользователей (вернулся ли через неделю).
- Конверсия в целевое действие (купил, оформил тикет, закрыл задачу).

### Системные

- Latency p50, p95, p99 (TTFT и общая).
- Стоимость на запрос, на пользователя, на день.
- Error rate (LLM ошибки, tool ошибки, timeouts).
- Кэш-хит rate (если используется prompt caching).

### Качественные

- % ответов, отмеченных как hallucination.
- % ответов с источниками.
- Доля переспрашиваний пользователя.

## Сбор обратной связи

UI: thumbs up/down + опциональный комментарий. Сохраняйте в БД вместе с сессией, промптом, моделью, версией.

```python
{
    "session_id": "...",
    "trace_id": "...",
    "user_id": "...",
    "feedback": "thumbs_down",
    "comment": "ответил не на тот вопрос",
    "prompt_version": "v3.2",
    "model": "claude-3-5-sonnet"
}
```

## A/B тестирование

Принцип тот же, что для обычных продуктовых A/B (см. урок 11 из курса DS). Особенности для LLM:

- Высокая дисперсия по стоимости и качеству. Sample size больше.
- Сложно "стандартизировать" пользователей — каждый запрос уникален.
- Может потребоваться stratification по типу запроса.
- Учитывайте сетевые эффекты: если пользователь видит ответы из двух разных версий — путаница.

Минимум 1–2 недели на сбор, иначе сезонность съест результат.

## Шадоу деплой

Перед полным A/B полезно прогнать новую версию параллельно со старой на 100% траффика, не показывая пользователю. Сравниваете на одинаковых запросах. Помогает поймать регрессии до того, как они дойдут до пользователей.

## Drift

Со временем распределение запросов меняется (новые темы, новый сленг). Метрики могут падать без изменений в коде. Регулярно (раз в месяц) пересматривайте eval-датасет и онлайн-метрики.

## Антипаттерны

- Считать только latency и cost, без качества.
- Thumbs down без причин в UI. Не знаете, что чинить.
- A/B на маленькой выборке. Результаты — шум.
- Не связывать онлайн-фидбек с оффлайн-evals. Можно добавлять "негативные" примеры в eval-датасет.
- Полагаться только на thumbs. Не каждый кликает.

## Практика

1. Добавьте thumbs up/down в UI вашего LLM-приложения. Логируйте в БД.
2. Постройте dashboard с latency p50/p95, % thumbs down, стоимость в день.
3. Запустите A/B двух промпт-версий на 2 недели. Замерьте разницу по конверсии (или CSAT).
4. Сделайте shadow deployment: новая модель обрабатывает запросы параллельно, но ответы не показываются. Сравните на 1000 запросах.
5. Возьмите 50 thumbs down с комментариями и добавьте в свой eval-датасет.
6. Настройте алерт: если % thumbs down растёт >X% за час — Slack-уведомление.

## Чек-лист

- [ ] Есть thumbs up/down + причина в UI.
- [ ] Дашборд с latency, cost, качеством — всегда под рукой.
- [ ] A/B тесты планируются заранее с расчётом sample size.
- [ ] Shadow deployment используется перед большими изменениями.
- [ ] Negative-фидбек регулярно перетекает в eval-датасет.
