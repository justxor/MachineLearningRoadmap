# 06. Реализация фичи end-to-end

## Принцип

Агент работает лучше всего, когда задача сформулирована как работа для мидл-разработчика: есть контекст, критерии приёмки, способ проверки.

## Схема: Explore → Plan → Code → Test → PR

### 1. Explore

```
> Я хочу добавить email-нотификацию при регистрации.
> Прочитай, как сейчас устроена регистрация и есть ли уже интеграции с email-провайдерами. Ничего не меняй.
```

### 2. Plan (в plan mode)

```
> Составь план реализации с разбивкой на файлы, которые потребуется затронуть.
> Отдельными блоками: изменения в схеме БД, HTTP-слой, сервисы, тесты. Какие риски?
```

Читаешь план, корректируешь, подтверждаешь.

### 3. Code

```
> Реализуй план. Начни с миграции БД и тестов.
> Коммить не надо — я проверю сам.
```

### 4. Test

```
> Запусти все тесты. Если что-то падает — почини. Не отключай тесты и не мокай без причины.
```

### 5. PR

```
> Сделай commit в Conventional Commits, push, открой PR через `gh pr create`.
> Описание PR: что добавлено, как проверять, риски.
```

## Шаблон задачи

```
Цель: <одно предложение>
Контекст: <@файлы, ссылки на ADR>
Критерии приёмки:
- тест X проходит
- ручная проверка: <команда или сценарий>
- логи выводят <что>
Ограничения:
- не менять публичный API
- обратная совместимость с v1
```

## Итерации

Агент выдаёт первую версию — ревьюшь, даёшь фидбэк:

-  «вынеси X в отдельный файл»
-  «тест слишком связан с реализацией, перепиши на уровень поведения»
-  «добавь лог ошибок в блоке catch»

Не принимай первый вариант «как есть». Средний фичинг берет 3–6 итераций.

## Работа с ветками

- Одна фича — одна ветка. Не давай агенту работать прямо в main.
- Коммить часто — легче откатиться.
- После каждой итерации: `git diff —— это то, что я хотел?`

## Антипаттерны

- «Сделай всё» без критериев приёмки — получишь мусор
- Работать в auto-accept на критичном коде без тестов
- Не читать дифф и сразу мерджить
- Смешивать рефакторинг и новую фичу в одном PR

## Практика

1. Выбери реальную задачу в своём проекте (issue/TODO).
2. Напиши формальный бриф по шаблону выше.
3. Пройди explore в plan mode, сохрани план в `/tmp/plan.md`.
4. Реализуй в отдельной ветке `feat/<name>`.
5. Получи первый вариант, дай минимум 3 корректирующих комментария.
6. Запусти тесты, попроси агента починить всё красное.
7. Открой PR через `gh pr create` (пусть агент сформирует описание).
8. Проведи self-review `/review` внутри Claude.

## Чек-лист

- [ ] Используешь шаблон брифа для фич
- [ ] Сначала plan, потом код
- [ ] PR содержит одну логическую измене́нию
- [ ] Не принимаешь первую версию «как есть»
- [ ] Читаешь дифф перед коммитом
