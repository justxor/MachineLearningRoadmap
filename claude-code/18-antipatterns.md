# 18. Антипаттерны и типичные ошибки

## Доверять без проверки

Claude Code пишет уверенно. Это не значит правильно. Читай дифф до коммита, запускай тесты в ручную хотя бы иногда.

## Работать без тестов

Агент не имеет «внутреннего ревьювера». Тесты — единственный внешний сигнал. Без них — плывёт в «должно работать».

## Сливать крупные PR без ревью

Агент при настойчивых промптах может выдать 1 000—строчный патч. Разбивай.

## Писать бесконечный CLAUDE.md

Чем больше файл, тем хуже он работает. 50–80 строк, только факты и запреты.

## --dangerously-skip-permissions на рабочей машине

Одна ошибка — и нет базы, нет ветки, нет ключей. Сандбокс или не включай.

## Прод БД на запись

Даже одно «DROP TABLE» посреди диалога. Read-only пользователь — обязательный минимум.

## Не ограничивать WebFetch

Агент по ссылке из issue может уйти на сайт с prompt injection и вернуться с «новыми инструкциями». Разрешай только доверенные домены.

## Одна сессия на всю неделю

Контекст раздувается, внимание падает, стоимость растёт. `/clear` на каждую новую задачу.

## Смешивать рефакторинг и фичи

Невозможно ревьюить и почти невозможно откатить. Разделяй.

## Принимать первый вариант

Агент пишет «рабочий» код, но не «лучший». 2–3 итерации фидбэка радикально меняют результат.

## Агент как поисковик

«Как написать X на Y?» — бери в обычный чат. Агент в репо — для работы с репо.

## Связывать выход агента в CI с деплоем

Авто-деплой с одного вызова LLM — плохая идея. Ревью и fix — да. Мердж и деплой делает человек.

## Конфиг в голове

Если ты единственный, кто знает «как у нас работает Claude Code» — это знание потеряется. Коммить в git: settings.json, .mcp.json, CLAUDE.md, .claude/commands/, .claude/agents/.

## Ожидания

- Не всё решается «одним промптом». Сложные задачи — это итерации.
- Агент хуже тебя в архитектуре, лучше в механической работе.
- Код, который ты не понимаешь, нельзя поддерживать.

## Практика

1. Отметь 3 антипаттерна выше, которые делаешь.
2. Напиши личный чек-лист в `~/.claude/CLAUDE.md` против своих ошибок.
3. Проведи ревью последних 5 PR от агента: где был «fake fix»?
4. Обнови deny-лист в settings.json по реальным инцидентам.
5. Настрой grep-хук на `it.only` и `describe.skip` перед коммитом.
6. Для команды: документ «что мы не разрешаем агенту».
7. Раз в месяц чисти audit.log и ищи странные паттерны.
8. Привычка «я вижу дифф» перед каждым коммитом.
